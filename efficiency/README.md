# R-KV fast-throughput reproduction (8×A100/A800)

This is the **fast** branch of `decodeatt`. Its goal is the number your research
harness cannot reach: the paper's **~2000–3000 tok/s** per-GPU decode
throughput, on the 8×A100/A800 node.

## Why a whole vLLM patch?

Your `scripts/eval.py` loop generates **one token at a time** in Python:
`for step in range(max_new)`, one `model(...)` forward per step, eager
attention for the `rkv`/`snapkv` arms (`eval.py:21` leaves them out of
`_FAST_ATTN_BACKENDS`). Per-step Python + eager attention caps this path at
**~50–100 tok/s** on an A800, and no config or batch-size change gets past it
— the harness is the bottleneck, not the algorithm.

The reference paper's number comes from a **patched vLLM v1** stack:

| vLLM feature | what it does for R-KV |
| --- | --- |
| continuous batching | all N prompts run in one batch, no per-token Python loop |
| PagedAttention | physical KV slots, compacted **in place** (the rkv patch) |
| cuda-graphs (PIECEWISE) | graph the non-attention parts of the layer; attention stays eager so the rkv hooks fire |
| FlashAttention backend | fast attention kernel |
| `VLLM_V1_R_KV_BUDGET` / `_BUFFER` | the compression is gated by env vars, not a Python policy loop |

So we vendor the reference integration (`efficiency/src/rkv/` + the 13-file
wiring patch) and build it against the pinned upstream vLLM `v0.25.1`.

## Reproduce

On the GPU node (8×A100/A800, CUDA toolchain present):

```bash
# 1. Build the patched vLLM (long; builds from source).
bash scripts/jiqun/rkv_fast_build.sh

# 2. Activate the build venv the script created.
source efficiency/.venv-rkv/bin/activate

# 3. Single-GPU sweep (your model + AIME).
bash scripts/jiqun/rkv_fast_bench_single.sh

# 4. 8-GPU data-parallel sweep.
bash scripts/jiqun/rkv_fast_bench_dp8.sh

# 5. Both + summarize.
bash scripts/jiqun/rkv_fast_bench_sweep.sh
```

To reproduce the reference paper's *exact* number (Qwen2.5-Math-7B +
GSM8K), run the single-GPU script with:

```bash
MODEL=Qwen/Qwen2.5-Math-7B-Instruct DATASET=gsm8k \
  bash scripts/jiqun/rkv_fast_bench_single.sh
```

## Understanding the numbers

- **R-KV's throughput gain is *not* a faster kernel** — it compacts the KV cache
  to `budget`+`buffer` entries, freeing paged slots and shrinking per-step KV
  bandwidth, so more requests fit and decode stays memory-bound-friendly.
- `VLLM_V1_R_KV_BUDGET` / `_BUFFER` **both > 0** = compression on. Either `0` =
  pure upstream vLLM (Full-KV baseline).
- Best-throughput flags: `VLLM_V1_R_KV_ASYNC=1` (+~17%), do **not** pass
  `--enforce-eager` (R-KV auto-selects PIECEWISE cudagraph).
- **AIME's long sequences (16k–19k) are where R-KV helps most** — KV is the
  bottleneck, and a 2048 budget is an ~8× KV cut. If you instead want the paper's
  headline number on short sequences, use the GSM8K / Qwen path above.
