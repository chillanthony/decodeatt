# KV eviction 实验框架加速方案

## 当前速度基准：A100 / MATH32 / budget 256

日志：`/root/data2/users/chenyanbo/decodeatt/logs/rkv_math32_b256.log`，环境为 `ssh a100`，共 32 道 `math500` 样本，arm 为 `full`、`snapkv@256`、`rkv@256`，当前仍是逐 token Python generation loop + `eager` attention 路径。

| arm | accuracy | mean gen len | mean final cache | mean elapsed / sample | log mean tok/s | weighted tok/s |
|---|---:|---:|---:|---:|---:|---:|
| full | 25/32 = 78.1% | 3856.6 | 3941.1 | 197.2s | 21.70 | 19.56 |
| snapkv@256 | 11/32 = 34.4% | 6604.3 | 299.4 | 321.7s | 21.83 | 20.53 |
| rkv@256 | 11/32 = 34.4% | 8712.7 | 304.0 | 477.2s | 21.12 | 18.26 |

简单判断：当前压缩策略没有带来明显 decode 吞吐提升，`snapkv@256` 和 `rkv@256` 的日志均值 tok/s 与 `full` 基本持平，`rkv@256` 还略慢。主要原因不是 KV 长度没有下降，而是当前框架瓶颈仍在逐 token Python 调度、`eager` attention、observation attention/logits 采集，以及 Python 侧 cache compact/统计开销。这个基准也说明，后续优化的第一目标应该先把不需要 observation 的路径切到 SDPA/FlashAttention，并降低 observation/debug 开销，而不是直接期待 eviction 本身提高当前 runner 的 tok/s。

## 当前判断

当前 `decodeatt / KVBench` 框架更偏算法对齐和可观测评测，不是最快的 serving 实现。主要慢点来自逐 token Python generation loop、`eager` attention、压缩前 observation attention/logits 采集、Python 侧手动 compact `past_key_values`，以及较细的 debug/metric 统计。

近期最现实的优化是先做 1/2/3：减少 observation 开销、把 eviction 更靠近 attention/cache update、让不需要 attention history 的策略走 SDPA/FlashAttention。vLLM/SGLang 风格 paged KV cache 是最大加速方向，但工程量明显更大。

## 方案 1：减少 observation 开销

状态：已完成（2026-07-13）。

现状：R-KV、SnapKV、H2O 只在压缩前的 observation window 内打开 attention/logits，这已经比全程记录 attention 轻很多。

已完成：

- 更精确地只在下一次会真正触发 eviction 前的 `window_size` 步收集 observation；如果缓存长度到下个 eviction 边界仍未达到触发阈值，就不打开 observation。
- 对不同策略分别设置 observation window：H2O 只需要 1 步，R-KV 使用 `alpha` 步，SnapKV 使用 `window_size` 步；`fullkv`、`streamingllm`、`random` 明确关闭 observation。
- 默认关闭不必要的 debug top-k token 解码；只有显式设置 `debug_topk > 0` 时才解码 token samples，中间分数记录仍只在 `debug_path/debug_dir` 打开时写入。

收益：中低风险，能减少额外 attention/logit 计算和 Python 统计开销。

优先级：高。已落地。

## 方案 2：把 eviction 逻辑内嵌到 attention/cache update

状态：已完成原型（2026-07-13）。

现状：框架在外部 `runner_token.py` 中收集 attention history，到 `evict_every` 时调用策略，然后手动 compact `past_key_values`。

官方式做法：在每层 attention forward/cache update 里维护 query cache，KV 长度超过 budget/buffer 后直接调用 `update_kv`，返回压缩后的 key/value。

需要改动：

- 新增 HuggingFace attention monkeypatch/integration 层。
- 给每层 attention 挂 policy object，例如 `RKVLayerCompressor`、`SnapKVLayerCompressor`。
- 在 attention forward 中直接拿 `query_states/key_states/value_states`。
- 在 cache update 后触发压缩。
- R-KV 额外维护最近 `alpha/window_size` 个 query。
- runner 侧减少 `_compact_cache()`、`attn_history`、部分 debug 逻辑。

收益：更贴近官方 HuggingFace 实现，减少外部 Python 调度和手动 cache gather 的管理成本。

风险：模型和 Transformers 版本耦合强；Llama、Qwen、Mistral 的 attention/cache 细节不同，维护成本高。

优先级：中高。建议先只支持一个主模型和一个策略，先做 `snapkv` 或 `streamingllm` 原型，再扩到 `rkv`。

## 方案 3：按策略启用 SDPA / FlashAttention

状态：已完成（2026-07-13）。

现状：为了拿 attention/logits，默认使用 `attn: eager`，这会拖慢所有策略。

可以区分策略：

- `streamingllm`、`window`、`random` 不需要 attention history，可以直接走 `sdpa` 或 `flash_attention_2`。
- `fullkv` 也不需要 eviction observation，可以走高性能 attention backend。
- `rkv`、`snapkv`、`h2o` 仍需要 observation，默认保留 `eager` 或只在 observation 段切换到可观测路径。

收益：对不需要 observation 的 baseline 会比较直接；对 cache-aware 策略收益取决于能否只在少数步回退到可观测路径。

风险：不同 backend 对 attention weights、cache position、mask 的支持不同。

优先级：高。已在 `scripts/eval.py --attn auto` 中落地：`fullkv/streamingllm/window/random` 走 `fast_attn`（默认 `sdpa`），`rkv/snapkv/h2o` 保留 `eager`。

4090 小模型测试：`Qwen2.5-0.5B-Instruct` 上 `fullkv` eager 约 36.07 tok/s，auto/sdpa 约 31.81 tok/s；auto 分组功能正确，但该环境下 SDPA 不比 eager 快。

## 方案 4：减少 debug 和 metric 统计开销

现状：长生成时记录 `evict_events`、cache 曲线、per-head 长度、debug token samples 等信息会增加 Python 和 CPU/GPU 同步开销。

可以做：

- 增加 `metrics_level: minimal | standard | full`。
- 默认只记录最终准确率、tokens/sec、peak memory、eviction 次数、最终 cache 长度。
- 只有 debug 模式才记录 token 文本、policy score、top-k 被保留/驱逐 token。

收益：实现简单，对大规模 sweep 有帮助。

风险：可观测性下降，需要保留 full 模式用于排查。

优先级：中。

## 方案 5：StaticCache + torch.compile

HuggingFace 官方文档提到 `StaticCache + torch.compile` 能加速 generation，因为静态 cache shape 更利于编译优化。

但当前 eviction 会动态 gather/compact KV cache，cache shape 和内容都在变化，和 StaticCache 的假设不完全匹配。

可尝试范围：

- `fullkv` baseline。
- `streamingllm/window/random` 这类规则简单、shape 稳定性更容易控制的策略。

收益：可能有中等收益，但不保证兼容当前动态 eviction。

优先级：中低。

## 方案 6：迁移到 vLLM / SGLang 风格 paged KV cache

这是最大加速方向，也是官方 R-KV 后续 serving 集成的核心方向之一。

核心做法：

- 使用 paged KV cache 管理物理 slot。
- eviction 后真正释放 dropped slot。
- 更新 request 到 KV slot 的映射。
- 接入 FlashInfer / paged attention / serving scheduler。
- 支持 batching 和多 request 调度。

收益：最大，尤其适合长 CoT、多请求、高吞吐场景。

风险：工程量最大，基本相当于做一个 serving integration，而不是简单改当前评测脚本。

优先级：长期。

- `Qwen2.5-0.5B-Instruct`，`sample n=2`，`max_new=256`，`budget=128`：`fullkv` 36.53 tok/s，Qwen2 integrated `snapkv@128` 63.83 tok/s。

## 方案 7：同题多候选 batch

状态：已完成（2026-08-12）。

目标：正式 pass@1 评测时，不再逐条串行生成同一道题的多个采样候选，而是在单张 GPU 上用静态 micro-batch 并行生成。

新增配置：

```yaml
generation:
  batch_size: 16
  num_return_sequences: 64
  seed_offset: 0
```

- `batch_size`：每次 GPU forward 并行生成的候选数。
- `num_return_sequences`：每道题总共生成的候选数；例如 64 个候选、batch 16 会执行 4 个 micro-batch。
- `seed_offset`：候选 seed 起始偏移，候选 seed 为 `seed + seed_offset + candidate_idx`。

实现内容：

- `kv_eviction/runner_token.py`：新增真实 batch generation，支持独立 RNG、finished mask、异步 EOS、候选级输出、batched KV gather。
- `kv_eviction/strategies/rkv_official.py`：R-KV importance、redundancy、per-layer/per-head top-k 支持 batch 维。
- `kv_eviction/strategies/snapkv.py`、`h2o.py`：attention baseline 的选择逻辑支持 batch。
- `kvbench/evaluator.py`：按 `batch_size` 拆分候选 micro-batch，并将结果汇总为题目级 pass@1。
- `kvbench/metrics.py`、`scripts/summarize_results.py`：支持候选级记录和汇总。
- `scripts/eval.py`：增加对应 CLI 参数。
- `tests/test_batch_generation.py`：增加 batch selection、KV compaction 和生成测试。

兼容性：`batch_size=1`、`num_return_sequences=1` 保持原有单轨迹行为；最后不足完整 batch 的候选自动使用较小 micro-batch。

## 方案 8：跨题长度分桶 batch

状态：已完成（2026-08-12）。

目标：当每道题只采样一次或同题候选不足以填满 GPU 时，将不同题目按 tokenized prompt 长度分桶后共同生成，减少串行题目调度和 padding 浪费。

新增配置：

```yaml
generation:
  problem_batch_size: 8
  prompt_bucket_size: 32
```

- `problem_batch_size`：一次并行处理的题目数。
- `prompt_bucket_size`：每次预取并按 prompt token 长度排序的题目数；`0` 表示自动设置。单进程默认取 `4 * problem_batch_size`，多卡动态调度默认取 `problem_batch_size`，避免单个 rank 提前领取过多题目。

跨题 batch 可以与同题多候选组合，最大 forward batch 为：

$$
\text{problem\_batch\_size} \times \text{batch\_size}
$$

实现内容：

- `kvbench/models.py`：对不同长度 prompt 做左侧 padding，生成 attention mask 和真实 prompt 长度。
- `kvbench/evaluator.py`：按 prompt token 长度排序、组成跨题 micro-batch，并在生成后恢复原题目顺序和候选归属。
- `kv_eviction/runner_token.py`：支持异构 prompt batch、逐请求 position ids、有效 KV mask、异步 EOS；已经结束的请求继续占用静态 batch 槽位，但其后续 filler KV 被 mask。
- `kv_eviction/strategies/rkv_official.py`、`snapkv.py`、`h2o.py`：importance、redundancy 和 top-k 显式屏蔽 prompt padding 与 EOS 后 filler，避免无效 KV 被评分或保留。
- `scripts/eval.py`、实验 YAML 和 `README.md`：增加跨题参数及运行说明。

运行示例：

```bash
PYTHONPATH=. uv run python scripts/eval.py \
  --config configs/experiments/math500_official_b1024.yaml \
  --problem-batch-size 8 \
  --prompt-bucket-size 32
```

也可与多候选组合：

```bash
PYTHONPATH=. uv run python scripts/eval.py \
  --problem-batch-size 4 \
  --batch-size 8 \
  --num-return-sequences 64
```
